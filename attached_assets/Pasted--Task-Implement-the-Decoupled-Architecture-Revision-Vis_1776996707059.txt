### 1. Task #78 – Standalone CTAD Architecture Workspaces

**Goal:** Allow users to create CTAD workspaces that are **not** bound to any ADC. The workspace identity is a new `architectureId` (opaque `-<8-hex>` suffix). Existing ADC‑bound bindings must continue to work unchanged (backward compatibility).

**Design decisions (from ARCHITECTURE.md):**
- New schema version `ctad-1.2`. The `CtadStoreDoc` gains an optional `architectures` map keyed by `architectureId`. The old `bindings` map remains.
- A new `CtadArchitectureShell` component is used for architecture‑first workspaces (route `/ctad/arch/:architectureId`). Do **not** add a mode switch to the existing `CtadShell`; keep them separate.
- Architecture IDs are generated by `ctad/architectureIdentity.ts`: `generateArchitectureId()` produces a string like `j3f2k1m4-a1b2c3d4`. No user‑provided slug is required; the name is stored separately.
- Migration from `ctad-1.1` → `ctad-1.2` is deterministic (reads old doc, adds `architectures: {}`).
- The CTAD entry page (`/ctad`) gains two tabs: “Decisions” (ADC‑bound workspaces from portfolio) and “Architectures” (standalone workspaces). The “Architectures” tab has a “+ New Architecture” button.

**Implementation steps:**

1. **Create `ctad/architectureIdentity.ts`**
   - Export `generateArchitectureId(): string` – 8 random hex chars + `-` + 8 random hex chars (use `crypto.randomUUID().slice(0,8)` for each part).
   - Export `isValidArchitectureId(id: string): boolean` – regex `/^[a-f0-9]{8}-[a-f0-9]{8}$/`.

2. **Extend `ctad/ctadTypes.ts`**
   - Add `CTAD_SCHEMA_VERSION = "ctad-1.2"`.
   - Add `ArchitectureWorkspaceEntry` type (fields: `architectureId`, `architectureName`, `createdAt`, `updatedAt`, `params`, `environments`).
   - Update `CtadStoreDoc` to have optional `bindings` and `architectures`.

3. **Modify `ctad/ctadStore.ts`**
   - Update `loadDoc()` to read v1.1 and migrate: if `schemaVersion === "ctad-1.1"`, convert to v1.2 with `architectures: {}` and write back on next mutation.
   - Add functions:
     - `createArchitecture(name: string): string` – generates ID, adds entry, writes.
     - `getArchitecture(id: string)`, `removeArchitecture(id)`, `listArchitectures()`.
     - `setArchitectureParam(id, paramId, value)`, `exportArchitectureState(id)` – reuse existing param validation.
     - Environment CRUD for architectures: `addArchitectureEnvironment`, `removeArchitectureEnvironment`, `setArchitectureEnvironmentKind`, etc. (mirror existing but keyed by `architectureId`).
   - Ensure legacy functions (`getBinding`, `setCtadParam`, etc.) continue to work on `bindings`.
   - Keep the same `useSyncExternalStore` subscription covering both stores.

4. **Create `pages/ctad/CtadArchitectureShell.tsx`**
   - A new page component for route `/ctad/arch/:architectureId`.
   - It is similar to `CtadShell` but:
     - Reads/writes via architecture‑first store functions.
     - No ADC binding panel.
     - Header shows architecture name (editable inline).
     - Renders the five collapsible CTAD sections (registry), environments panel, and a live `CTAD_STATE` JSON preview.
     - Does **not** include CNCF Apply panels (those remain on ADC‑bound shells).
   - Use existing shared UI components where possible.

5. **Update `pages/ctad/CtadEntry.tsx` (landing page)**
   - Add a tab bar: “Decisions” (shows `listEntries()` from portfolio) and “Architectures” (shows `listArchitectures()`).
   - “Architectures” tab: display list with name, creation date, and a button “New Architecture”. Clicking a row navigates to `/ctad/arch/:id`.
   - The verbatim empty‑state sentence “CTAD requires an approved architectural decision.” now only applies to the “Decisions” tab when no portfolio entries exist. For the “Architectures” tab, show a neutral empty prompt like “No architecture workspaces yet.”

6. **Update routes in `App.tsx`**
   - Add `<Route path="/ctad/arch/:architectureId" component={CtadArchitectureShell} />`.
   - Keep existing `/ctad/:adsId/:adsVersion` route.

7. **Update build‑time invariants**
   - `ctad/ctadGrammarInvariants.ts`: accept schema `ctad-1.2`. Validate that `architectures` entries have required fields and no `adsId`/`adsVersion`. Keep the five‑section registry lock.
   - `ctad/ctadIsolationInvariants.test-shape.ts`: no changes needed yet (the architecture shell does not import portfolio).

8. **Update vocabulary guard**
   - Add new UI strings (“Architectures”, “New Architecture”, “Architecture name”, etc.) to `assertAllCtadLanguage` calls in the relevant modules.

### 3. Task #82 – Technology‑Aware Semantic Node Binding (ACW Phase 5)

**Goal:** ACW authored nodes can optionally be bound to a CTAD parameter value, so that if the CTAD parameter changes, the node’s label and icon automatically update.

**Design decisions (from ARCHITECTURE.md):**
- `AcwNode` gains two new **optional** fields: `boundParam?: { sectionId, paramId, optionValue }` and `boundTechnologyCategory?: string`.
- Icons come from `lucide-react` via `acw/icons/iconRegistry.ts`. The icon registry maps technology categories (e.g., `database`, `frontend`, `backend`, `server`) to lucide icon components.
- `acw/semantic/techNodeBinding.ts` is the only ACW module allowed to import `@/ctad/ctadRegistry`. It reads `findSectionForParam` and the option list to validate the binding, and returns a display label and icon.
- ACW schema remains `acw-1.0` (optional additive fields, read‑validator relaxed).

**Implementation steps:**

1. **Create `acw/icons/iconRegistry.ts`**
   - Export a `Record<string, React.FC>` mapping category strings to lucide icons (e.g., `database` → `Database`, `server` → `Server`, `frontend` → `Layout`, `backend` → `Codepen`, `container` → `Box`, `message‑queue` → `MessageCircle`, etc.).
   - These are **generic** icons, no vendor logos.

2. **Create `acw/semantic/techNodeBinding.ts`**
   - Export `resolveBoundNode(boundParam, boundTechnologyCategory): { label: string; Icon: React.FC | null }`.
   - Validation: if `boundParam` is given, check that `sectionId` exists (via `findSectionForParam` in `ctadRegistry`), and that `optionValue` is in the param’s options. If invalid, fall back to the node’s existing `label` and no icon.
   - If `boundTechnologyCategory` is given, resolve icon from `iconRegistry`; otherwise use generic icon for the param’s section (e.g., `infrastructure` → `Server`).

3. **Extend `acw/acwGrammar.ts` and `acw/acwValidator.ts`**
   - Add `boundParam?` and `boundTechnologyCategory?` to `AcwNode` type.
   - Update `isValidWorkspace` and `assertAllowedFields` to accept these new optional fields (relaxing the schema).

4. **Update `components/acw/AuthoringPanel.tsx`**
   - When adding/editing a node, optionally show a “Bind to CTAD parameter” section where the user can select a section, param, and option. This is optional; if not set, the node remains a plain label.

5. **Update canvas rendering**
   - In `InteractiveCanvas2D` and `Canvas3DStructural`, when rendering a node, call `resolveBoundNode` to get the display label and icon, overriding the node’s manual label. This ensures visual consistency.

6. **Update invariants**
   - `acwGrammarV2Invariants.test-shape.ts`: add probe (7) to verify that the read‑validator accepts documents with `boundParam` and `boundTechnologyCategory`.
   - `acw/acwIsolationInvariants.test-shape.ts`: ensure that ONLY `acw/semantic/techNodeBinding.ts` is allowed to import `@/ctad/ctadRegistry` (all other ACW files still forbidden from decision pipeline).
