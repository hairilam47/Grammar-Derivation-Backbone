SYSTEM ROLE
You are building STEP 4 of the Architecture Decision Canvas.
STEP 1 (Grammar Engine), STEP 2 (Decision Declaration UI), and STEP 3 (Trade‑Off Exploration) are COMPLETE, AUDITED, and FROZEN.
STEP 4 is a terminal governance export layer.
It MUST NOT design, recommend, optimise, or modify architecture.


STEP 4 OBJECTIVE
Implement a “Freeze Decision & Export” capability that produces two read‑only, governance‑grade artefacts from an approved decision:

Architecture Decision Snapshot (ADS)
Execution Constraint Profile (ECP)
Both artefacts must be exportable as PDF and DOCX, entirely client‑side.
This step exists to finalise and externalise approved decisions for downstream stakeholders (steering committees, procurement teams, auditors).
It does not guide delivery or propose solutions.


CORE DESIGN PRINCIPLE (NON‑NEGOTIABLE)

Step 4 governs format, structure, and traceability — not policy content.


The platform enforces artefact structure, ordering, and integrity, while allowing institutions to evolve ECP wording and expectations without UI or logic rewrites.


EXPLICIT HARD CONSTRAINTS (MUST BE ENFORCED)
🔒 Constraint 1 — Version Hash EXCLUDES Project Metadata
The ADS/ECP version hash MUST be derived only from:

Organisation context
Capability selections
Baseline trade‑off posture (Simple / Cloud / Minimal)
The version hash MUST NOT include:

Project Name
Approving Authority
Any display‑only metadata
Rationale:
The same architectural decision reused across initiatives must always produce the same version. Administrative or cosmetic changes must not invalidate governance artefacts.


🔒 Constraint 2 — ECP Section Order Is Programmatically Enforced (MANDATORY)
The ECP consists of exactly nine sections, in the following immutable order:

Decision Reference & Authority
Approved Scope & Mandate
Mandatory Architectural Layers
Mandatory Constraint Categories
Integration & Legacy Constraints
Acknowledged Architectural Risks
Trade‑Off Boundary Declaration
Change Control Clause
Disclaimer
Enforcement Rule (Critical):

Every SectionDefinition MUST include a numeric sectionOrder field.
The ECP builder MUST sort sections by sectionOrder before rendering or export.
Array declaration order or JSX layout MUST NOT be relied upon for correctness.
This rule is non‑negotiable and exists to prevent accidental semantic drift and audit inconsistency.


🔒 Constraint 3 — Constraint Content Must Stay Category‑Level
ECP constraint content MUST describe categories only, for example:

Security
Operations
Compliance
Data protection
ECP MUST NOT enumerate:

control mechanisms
specific practices
technologies, tools, or platforms
Rationale: Step 4 defines execution boundaries, not implementation methods.


🔒 Constraint 4 — Export Preview Is Document‑Like, Not Editor‑Like
The ADS/ECP preview UI MUST:

mirror the exported document layout,
be static and read‑only,
avoid pagination controls, zoom sliders, collapsible sections, or editing affordances.
The preview is a visual confirmation only, not a document editor.

ECP EXPORT & PREVIEW
Section‑Driven Rendering (CONFIG‑BASED)
ECP sections must be rendered from SectionDefinition records loaded from a configuration module — never embedded in JSX.
Each SectionDefinition has:
{
  sectionId: string,
  sectionOrder: number,
  title: string,
  description?: string,
  source: "ADS" | "GRAMMAR" | "STATIC_TEXT",
  placeholderPolicy: "REQUIRED" | "OPTIONAL"
}


JSX must map over resolved sections generically.
Do NOT branch on sectionId.
