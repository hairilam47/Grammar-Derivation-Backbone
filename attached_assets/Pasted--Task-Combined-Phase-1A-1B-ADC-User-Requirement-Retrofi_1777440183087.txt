## Task: Combined Phase 1A + 1B – ADC User Requirement Retrofit & Configurable SRS Export

You are working on `Grammar-Derivation-Backbone`. This task is a major rework of the ADC wizard and introduces a configurable IEEE‑830‑style SRS document export. It is one integrated implementation, but logically divided into two stages.

**Core principle:** The new data model (User Requirements, Modules, Contracts) and the wizard UI are built first, without any dependency on the SRS template. The SRS export engine is a separate module that reads the stored data and formats it according to a **mutable template configuration**. The template never defines the UI or workflow; it only controls how existing data is rendered into a document.

Requirements Store
File: governance/requirementsStore.ts

Key: adc.requirements.v1

Schema version: req‑1.0

Shape:

ts
interface UserRequirement {
  id: string;                // "req‑001"
  title: string;
  description: string;
  type: 'functional' | 'non‑functional' | 'constraint' | 'hardware';
  priority: 'low' | 'medium' | 'high' | 'critical';
  moduleId?: string;        // references Module, or null → draft
  hardwareDetails?: {
    itemName: string;
    model?: string;
    quantity: number;
    unitCost?: number;
    totalEstimatedCost?: number;
    notes?: string;
  };
  status: 'draft' | 'reviewed' | 'approved' | 'frozen';
  useCaseIds?: string[];
  componentIds?: string[];
  createdAt: string;
  updatedAt: string;
}
Functions: saveRequirement, deleteRequirement, getRequirement, listRequirements, approveRequirement, freezeRequirements.

Business rules enforced:

If moduleId is missing on save, status is forced to draft (even if caller passes another status).

Only approved requirements can be frozen; freezeRequirements rejects any with status !== 'approved'.

When type === 'hardware', hardwareDetails must be present and valid (quantity > 0).

Stage B – Configurable IEEE‑830 SRS Export Engine
B1. Template Configuration
Create a mutable configuration file governance/srsTemplateConfig.ts that defines how to map the live data to an IEEE‑830 document structure. It does not influence any UI or workflow. It is pure mapping.

The configuration is a TypeScript object conforming to:

ts
interface SrsTemplateConfig {
  metadata: { standard: string; version: string; lastUpdated: string };
  sections: SrsSection[];
}

interface SrsSection {
  title: string;                   // e.g. "1. Introduction"
  subsections: SrsSubSection[];
}

interface SrsSubSection {
  title: string;                   // e.g. "1.1 Purpose"
  contentGenerator: string;        // key of a generator function (see below)
  fields?: string[];               // optional: which fields to pull from the WorkItem
}
Generator keys correspond to pure functions in governance/srsGenerators.ts that take the WorkItem, list of Modules, list of Requirements, CTAD state, and ACW workspace (if available) and return a string or object to be rendered.

Example:

"purpose" → generates text from WorkItem’s purpose field.

"scope" → generates product scope from WorkItem description.

"systemFeatures" → iterates Modules and their linked requirements to build a list of features.

"hardwareInterfaces" → lists hardware requirements with details.

"nonFunctional" → lists non‑functional and constraint requirements.

"glossary" → collects unique terms from all requirement descriptions.

The default configuration must implement the IEEE 830 skeleton from the uploaded srs_template-ieee.pdf, with all sections mapped to available data. Empty sections are still generated with a placeholder "[No data]" to match the standard.

B2. Export Engine
File: governance/ieeeSrsExporter.ts

Exports a function exportSRS(format: 'pdf' | 'docx') that:

Reads the template configuration.
Fetches all required data (WorkItem, Modules, Requirements, etc.).
Iterates through the template sections and calls the appropriate generator for each.
Assembles a document with proper headings, numbering, and tables.
Uses the existing jspdf for PDF and docx libraries for DOCX.
The document metadata (title page, revision history) is auto‑populated from the WorkItem and contract.

The final document includes the standard appendix for Glossary and TBD list (auto‑collected from unresolved references).

B3. UI Integration
Add a "Generate SRS" button in the Requirements Capture screen and/or the Freeze screen. It opens a dropdown to select PDF or DOCX, then triggers the export.

The button is available even before freezing, to preview the SRS. The generated document should include a prominent "DRAFT" watermark if the requirements are not frozen.

All generated labels in the export UI must pass vocabulary guard.

B4. Evolvability
The template configuration can be modified at any time. Future updates to IEEE 29148 or custom corporate templates only require editing srsTemplateConfig.ts and possibly adding new generator functions.

The export engine treats the configuration as the definition of the document structure; no hard‑coded section ordering.

Organisations can later clone and override the configuration per WorkItem if needed (future enhancement).
