Phase 1B – Configurable IEEE‑830 SRS Export Engine (if not already done)
Context: Task #133 (Phase 1A) is complete—the Module Catalogue, Requirements Store, Requirements Contract Store, and the new 5‑screen wizard are all merged and working. The SRS export engine must now be built on top of that real data.

What the Replit agent must deliver
governance/srsTemplateConfig.ts – a mutable configuration object of type SrsTemplateConfig describing the IEEE‑830 skeleton. Each sub‑section maps to a contentGenerator string.

governance/srsGenerators.ts – pure generator functions (e.g., purpose, scope, systemFeatures, hardwareInterfaces, nonFunctional, glossary, tbdList) that return strings or structured blocks from the live data.

governance/ieeeSrsExporter.ts – exportSRS(format: 'pdf' | 'docx') reads the config, walks the sections, calls the generators, and assembles a PDF (via jspdf) or DOCX (via docx) with proper hierarchical numbering, tables, title page, revision history, glossary, and TBD list.

DRAFT watermark – the exporter must detect when any requirement is not frozen, and render a diagonal “DRAFT” watermark on every page (PDF) or header/footer marker (DOCX). Frozen contracts suppress the watermark.

UI button – a “Generate SRS” button (with PDF/DOCX dropdown) on both the RequirementsCapture screen and the FreezeScreen. The button calls exportSRS and triggers a browser download.

Vocabulary guard – all new static labels in the UI (button text, dropdown items) must be asserted via assertAllGovernanceLanguage.

No store modifications – the exporter only reads existing stores; it never writes.

Evolvability – changing the template config or adding a new generator function must affect the export without changing any other code.

governance/storageKeyUtils.ts with getScopedKey(baseKey, orgId, workItemId).

All existing stores (portfolio, signals, requirements, module catalog, CTAD, ACW, view‑state, track 3 prefs, attachments, OUs) must be updated to use scoped keys.
