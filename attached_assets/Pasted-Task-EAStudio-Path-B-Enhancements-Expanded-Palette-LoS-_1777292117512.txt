Phase 2 – Level of Specification (LoS) Framework
Goal
Introduce three architectural levels (L1 Business, L2 Application, L3 Technology) that the user can toggle. The canvas automatically switches between 2D and 3D, and when moving to L3, it generates deployment‑level children from CTAD parameter bindings.

Steps
Expand the ACW grammar (acw/acwGrammar.ts):

Add an optional field lodRange?: [number, number] to AcwNode. Default if absent is [1, 3] (visible on all levels).

Widen the store’s ALLOWED_NODE and read‑validator to accept lodRange.

Do not change the schema version; it stays acw‑1.0.

Modify enumerateLensVisibility (in acw/acwLensStructure.ts) to accept an optional currentLodLevel parameter (1, 2, or 3) and filter nodes whose lodRange does not include that level. Edges are only visible if both endpoints are visible at the current LoS.

Add LoS selector UI to the EAStudio top bar (or as a floating overlay):

Three buttons: “Business” (L1), “Application” (L2), “Technology” (L3).

Active state stored in acwViewState as a new per‑lens field activeLodByLens (default 2 for EAStudio).

The selector is visible only when the EAStudio lens is active.

Canvas mode switching:

When currentLod is 1 or 2, render the 2D canvas (the existing domain grid).

When currentLod is 3, instantiate the 3D structural canvas (Canvas3DStructural) in the Technology domain quadrant, replacing its 2D embed. The other quadrants (Business, Data, Application) remain 2D but are filtered to show only nodes with lodRange covering level 3 (e.g., they may show their high‑level containers).

Alternatively, for simplicity, when switching to L3, the entire view could switch to a full‑screen 3D canvas that shows all L3‑visible nodes across all domains, but the per‑quadrant approach better matches the EAStudio layout. We'll go with a full‑screen 3D for L3 as the first implementation: L3 shows a single 3D canvas occupying the whole window, with all L3‑visible nodes from all domains rendered in 3D. The quadrant grid is hidden. This is easier and more dramatic.

Auto‑generation of L3 nodes (acw/semantic/ctadToAcwSeed.ts):

Create a pure function generateL3Nodes(architectureId: string): void that reads the architecture’s CTAD state (through getArchitecture or exportArchitectureState from ctadStore), examines all L2 nodes with boundParam, and creates corresponding L3 child nodes if they don’t already exist.

Example rule: If a System node has boundParam referencing hostingModel: kubernetes, create a ComputeNode (Kubernetes Cluster) as a child, and inside it a Component (Container) representing the runtime instance.

The generated nodes carry lodRange: [3, 3] so they only appear at L3.

The function must be called when the user switches to L3 for the first time for that architecture. On subsequent L3 switches, only new missing nodes are added (idempotent based on stable ID derivation from the parent + param).

The generated nodes are persistent (store‑created) so they survive navigations.

Update invariants – add probes to acwGrammarV2Invariants.test-shape.ts:

Accept nodes with lodRange: [1, 2], lodRange: [2, 3], etc., and absence.

Reject invalid lodRange (negative, out of bounds, non‑array).

Verify that generateL3Nodes does not produce cycles or illegal containment.

Ensure ACW isolation still passes.
